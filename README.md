# tulaufa

Сайтик бежиного луга

## Требования

- Node.js 22 или новее (CI собирает на 22)
- npm

## Разработка

После установки зависимостей через `npm install` запустите сервер разработки:

```sh
npm run dev

# или запустите сервер и сразу откройте приложение в новой вкладке браузера
npm run dev -- --open
```

## Сборка

Чтобы собрать продакшен-версию приложения:

```sh
npm run build
```

Готовый сайт появится в каталоге `build/` (он в `.gitignore` — в репозиторий не коммитится).
Посмотреть собранную версию можно командой `npm run preview`.

## Маршрут /minecraft-admin

Страница `/minecraft-admin` управляет сервисом `minecraft.service` на сервере:
статус, старт/стоп/рестарт и живой лог. Сама страница статическая и ничего не
умеет — вся работа у демона
[tulaufa-mine-go](https://github.com/indiagolph99/tulaufa-mine-go), который
в продакшене стоит за nginx на `/api/mc/*`.

Маршрут намеренно не залинкован с главной, а главная страница остаётся
публичной: авторизация закрывает только API.

### Как разрабатывать локально

Нужны обе половины: демон и дев-сервер сайта. Systemd не требуется — в репозитории
демона есть заглушка, которая изображает `minecraft.service`.

**1. Запустите демон** (в папке `tulaufa-mine-go`):

```sh
# пароль придумываете сами; хеш печатается в stdout
export ADMIN_PASSWORD_HASH="$(go run ./cmd/tulaufa-mine hash)"

export MC_CTL="$PWD/testdata/mc-ctl-stub"   # заглушка вместо systemd
export ALLOWED_ORIGIN=http://localhost:5173 # адрес дев-сервера Vite
export SECURE_COOKIE=false                  # локально нет TLS
go run ./cmd/tulaufa-mine
```

Постоянного пароля нет и быть не должно: `ADMIN_PASSWORD_HASH` живёт только в
вашей сессии терминала. На сервере хеш лежит в `/etc/tulaufa-mine/env`.

**2. Запустите сайт** (в этой папке):

```sh
npm run dev
```

Откройте <http://localhost:5173/minecraft-admin> и войдите тем паролем, для
которого сделали хеш.

Дев-сервер проксирует `/api/mc` на `127.0.0.1:8787` — это настроено в
`vite.config.ts` и заменяет nginx. `changeOrigin` выключен намеренно: демон
сверяет заголовок `Origin` с `ALLOWED_ORIGIN`, поэтому подменять его нельзя.

### Если что-то не работает

| Симптом | Причина |
|---|---|
| `403 missing Origin header` | запрос идёт не из браузера или `changeOrigin` включили |
| `403 origin not allowed` | `ALLOWED_ORIGIN` не совпадает с адресом дев-сервера |
| Вход проходит, но следующий запрос `401` | не выключен `SECURE_COOKIE` — браузер не хранит `Secure`-cookie на http |
| `429` при входе | сработало ограничение: 5 попыток в минуту |
| Лог пуст | заглушка выдаёт строку раз в 0.2 с; проверьте, что `MC_CTL` указывает на неё |

## Как вносить изменения

Единственная долгоживущая ветка — `main`. Всё остальное создаётся под задачу и
удаляется после вливания.

1. Создайте ветку от свежего `main`:

   ```sh
   git switch main && git pull
   git switch -c feature/краткое-описание
   ```

   Префиксы: `feature/` — новое, `fix/` — исправления, `chore/` — рутина
   (конфиги, зависимости, CI), `docs/` — документация.

2. Перед коммитом убедитесь, что сборка проходит:

   ```sh
   npm run check     # проверка типов
   npm run build
   ```

3. Откройте PR в `main`. На каждый PR автоматически запускается workflow **CI**:
   он ставит зависимости, прогоняет `npm run check` и `npm run build`.
   Вливайте PR после ревью и зелёного CI.

Коммит в `main` напрямую ничего не выкатывает: деплой запускается только вручную,
см. ниже.

## Как выкатить релиз

Деплой всегда ручной и всегда с ветки `main`.

1. **Actions → deploy → Run workflow**, ветка `main`.
2. Запуск остановится со статусом «Waiting for review» — это гейт окружения
   `production`. Запросить аппрув у @indiagolph99.
 
Из командной строки то же самое:

```sh
gh workflow run "deploy" --ref main
```

История выкаток — во вкладке **Deployments** репозитория.

### Откат

Тег указывает на конкретный коммит, поэтому откат — это обычный откат кода:
верните `main` к нужному состоянию (через `git revert` и PR) и запустите деплой снова.
Отдельной кнопки отката нет (пока)
